KPI Dashboard — API reference (HELP)

Companion machine-readable spec: openapi.yaml (OpenAPI 3.0).

Who this page is for. An AI agent (or any client/collector) that needs to read the configuration, create/delete metrics and push daily snapshots. It is deliberately written in plain, unambiguous terms. It ships next to the API (deploy/api/HELP.html) and is deployed with it.

1 · Purpose & mental model

The dashboard shows a 0–100 aggregate index: a weighted mean of per-metric scores computed from raw daily values and per-metric thresholds. Everything is config-driven and stored in SQLite:

TableContentManaged by
configSingle row: dashboard title, subtitlePOST /api/config
config_metricsOne row per metric: key, name, why, G/Y/O thresholds, weightPOST /api/config/metrics and DELETE /api/config/metrics/{key}
metricsDaily raw value + computed score per metricPOST /api/metrics (snapshot)
snapshotDaily aggregate index + zonePOST /api/metrics (snapshot)

Important: there are no hardcoded/business metric defaults in the code. To define what the dashboard measures you must create metrics through the API (section 5). The frontend is fully generic and renders whatever GET /api/config returns.

2 · Base URL & authentication

The app may be installed in the webroot or under a subfolder (default deployment: /dashboard/). All API paths below are relative to that base:

BASE = https://your-domain.com/dashboard     # if deployed at the webroot: https://your-domain.com

Two authentication modes, used as follows:

ModeUsed forHeader
BearerAll writes (POST config, POST/DELETE metrics config, POST snapshots) and reads (GET config, GET latest, GET history) — the collector/feeder uses its token for everythingAuthorization: Bearer <API_TOKEN>
BasicReads only, for humans/browsers: GET config, GET latest, GET historyAuthorization: Basic <base64(user:pass)> (or -u user:pass)

Reads accept either mode: a valid Bearer token or Basic credentials. Writes always require the Bearer token. A GET without a valid token/credentials returns 401. 

# write example
curl -X POST "$BASE/api/config/metrics" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{...}'

# read examples: the SAME token works for reads too (no Basic needed)
curl -H "Authorization: Bearer $TOKEN" "$BASE/api/config"
curl -H "Authorization: Bearer $TOKEN" "$BASE/api/metrics/latest"
curl -u "$USER:$PASS" "$BASE/api/config"        # or with Basic credentials

4 · Metric definition (the only configuration you need to understand)

Each metric is defined by one object. Thresholds use G = green, Y = yellow, O = orange; red is everything above O (4 zones, open-ended red).

FieldTypeRequiredMeaning
keystringyesUnique id. URL-safe: letters, digits, _ . -, not starting with a separator. E.g. orders_to_fulfil
namestringno*Label shown on the dashboard (default: the key)
whystringno*Short “why it matters”, shown under the name (default: empty)
Gnumber ≥ 0yesGreen threshold: value in [0..G] → green zone (score 0–25)
Ynumber ≥ 0yesYellow threshold: value in [G+1..Y] → yellow (score 26–50)
Onumber ≥ 0yesOrange threshold: value in [Y+1..O] → orange (score 51–75); above O → red (76–100)
weightnumber ≥ 0no*Relative importance in the aggregate (default: 1)

* name/why default sensibly; weight defaults to 1. Missing/empty name falls back to the key.

Score & aggregate — exact rules

  • Per metric, the raw value maps to a 0–100 score by piecewise-linear interpolation over the bands: green [0,G]→0–25, yellow [G+1,Y]→26–50, orange [Y+1,O]→51–75, red [O+1, 2·(O+1)]→76–100 (saturates at 2·(O+1)). If G=0 green only applies to value 0.
  • Aggregate index = weighted mean: 
    index = round( Σ(scoreᵢ × weightᵢ) / Σ(weightᵢ) , 1 )
  • Weights never need to sum to 1.00. They are normalised by their total at calculation time. If all weights are 0, the plain average of the scores is used.
  • Zones from the index: green ≤25, yellow ≤50, orange ≤75, red >75.

5 · Suggested workflow for an agent / collector

0) Authenticate. You need the operator-provided Bearer token. Use it for writes and reads; reads also accept Basic credentials (humans).

1) Inspect the current setup: GET /api/config. It returns {"title":…,"subtitle":…,"metrics":{"key":{name,why,G,Y,O,weight},…}}.

2) Create/update each metric you want to track with POST /api/config/metrics (repeat per metric). Re-POSTing the same key updates it; the frontend adapts automatically.

3) (Optional) set the dashboard title/subtitle with POST /api/config.

4) Every day, push the snapshot: POST /api/metrics with {"date":"YYYY-MM-DD","metrics":{"key":rawValue,…}}. Re-POSTing the same date replaces that day (idempotent) — use it to correct mistakes.

5) Read back: GET /api/metrics/latest and GET /api/metrics?from=…&to=… to verify. Responses include, per metric: value (raw), score (0–100) and zone.

6 · Endpoint details

GET /api/config — read the active setup

Auth: Basic or Bearer. Returns the title/subtitle and every configured metric.

# with the collector token (recommended for agents/feeders)
curl -H "Authorization: Bearer $TOKEN" "$BASE/api/config"
# or with Basic credentials (humans)
curl -u "$USER:$PASS" "$BASE/api/config"

200 {
  "title": "Production Dashboard",
  "subtitle": "updated daily at 20:00",
  "metrics": {
    "orders": {"name": "Orders to fulfil", "why": "fast fulfilment keeps trust", "G": 0, "Y": 2, "O": 5, "weight": 0.6},
    "emails": {"name": "Emails to triage", "why": "quick replies improve trust", "G": 5, "Y": 15, "O": 30, "weight": 0.4}
  }
}

POST /api/config — set title/subtitle

Auth: Bearer. Accepts only title and/or subtitle. Sending a metrics field is rejected (metrics use the dedicated endpoints).

curl -X POST "$BASE/api/config" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"title": "Production Dashboard", "subtitle": "updated daily at 20:00"}'

200 {"ok": true, "title": "Production Dashboard", "subtitle": "updated daily at 20:00"}

POST /api/config/metrics — create/update one metric

Auth: Bearer. Upsert by key: unknown key → created; existing key → updated. Validations: key URL-safe, thresholds numeric ≥ 0, weight ≥ 0.

curl -X POST "$BASE/api/config/metrics" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"key": "orders", "name": "Orders to fulfil", "why": "fast fulfilment keeps trust",
       "G": 0, "Y": 2, "O": 5, "weight": 0.6}'

200 {"ok": true, "created": true, "key": "orders",
     "metric": {"name": "Orders to fulfil", "why": "…", "G": 0, "Y": 2, "O": 5, "weight": 0.6}}

DELETE /api/config/metrics/{key} — delete a metric

Auth: Bearer. Removes the metric from the active configuration. Historical rows are kept but hidden from GET responses; re-creating the key later restores them.

curl -X DELETE "$BASE/api/config/metrics/orders" -H "Authorization: Bearer $TOKEN"

200 {"ok": true, "key": "orders", "deleted": true}
404 {"error": "metric not found: orders"}

POST /api/metrics — save/replace a daily snapshot

Auth: Bearer. The metrics object must contain exactly all active keys (missing → 400; unknown extra keys are ignored). The optional index field is ignored: the server recomputes scores and the aggregate.

curl -X POST "$BASE/api/metrics" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"date": "2026-09-01", "metrics": {"orders": 2, "emails": 10}, "index": 0}'

200 {"ok": true, "date": "2026-09-01", "index": 55.8, "zone": "orange"}

If no metrics have been configured yet, the API answers 400 with “no metrics configured yet: create them first with POST /api/config/metrics”.

GET /api/metrics/latest — latest snapshot

Auth: Basic or Bearer. Used by the dashboard gauges. Contains date, index, zone and per-metric {value, score, zone}.

GET /api/metrics?from=&to= — history

Auth: Basic or Bearer. Optional from/to (YYYY-MM-DD); default = last 30 days (inclusive). Returns a chronological array of daily snapshots.

# with the collector token
curl -H "Authorization: Bearer $TOKEN" "$BASE/api/metrics?from=2026-08-01&to=2026-08-24"
# or with Basic credentials
curl -u "$USER:$PASS" "$BASE/api/metrics?from=2026-08-01&to=2026-08-24"

7 · Errors & conventions

StatusMeaning
200Success (body described per endpoint)
400Invalid input — body {"error": "human readable reason"}
401Missing/wrong token (writes) or credentials (reads) — {"error":"unauthorized"}
404Unknown endpoint or metric key not found
405Method not allowed on that path
500Server/database error
  • Bodies are always JSON, UTF-8.
  • Dates are always YYYY-MM-DD (a real calendar date).
  • GET responses only include metrics that are still in the active configuration.
  • Snapshots are idempotent per date: re-POSTing the same date atomically replaces it.
