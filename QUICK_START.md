# KPI Dashboard — QUICK START (post-upload / server setup)

This guide explains **what to do once the files are already in their final
remote folder** (the folder your FTP/FTPS deploy targets — by default
`<FTP home>/dashboard/`). It only covers the **server-side tasks** needed to
make the dashboard live.

With the `first_setup.php` bootstrap, **one single POST** does the whole
one-time setup: it generates the Bearer token, the viewer password file, the
root `.htaccess` and seeds the database. Afterwards none of those files are
ever overwritten by later deploys.

> Full API reference: `HELP.html` in `/api/` (also `openapi.yaml`).

---

## 0 · What the deploy puts on the server (and what it never touches)

Your remote folder after the deploy:

```text
…/dashboard/               <- "APP_DIR" in this guide (webroot of the app)
├── index.html             # compiled Vue frontend
├── assets/…               # hashed JS/CSS bundles
├── example.htaccess       # ⭐ Basic Auth TEMPLATE (copied to .htaccess by
│                          #    first_setup.php with the real AuthUserFile)
├── first_setup.php        # ⭐ one-time bootstrap — run it ONCE (step 1)
├── api/
│   ├── .htaccess          # rewrites /api/* → metrics.php
│   ├── metrics.php        # the whole backend (API)
│   ├── HELP.html          # API reference
│   └── openapi.yaml       # OpenAPI spec
└── data/
    ├── .htaccess          # denies web access to this folder
    └── seed.sqlite        # seed (test metrics + history) for new installs
```

The deploy **deliberately never uploads** these four files — they are
server-owned and created **once** by `first_setup.php`, and they are never
part of the deployed bundle (so they are never in the FTPS action's
sync-state and can never be overridden or deleted by a later release):

| Server-owned file | Created by | Holds |
|---|---|---|
| `data/config.php` | `first_setup.php` | `API_TOKEN` (Bearer), DB path |
| `.htpasswd` | `first_setup.php` | viewer (Basic Auth) credentials — same folder as `.htaccess` |
| `.htaccess` (root) | `first_setup.php` | Basic Auth, **copied from `example.htaccess`** with the real `AuthUserFile` path |
| `data/kpi.sqlite` | `first_setup.php` | the **live** database (metrics + data points) |

Because the root `.htaccess` doesn't exist until `first_setup.php` runs, run
it **right after the first deploy** (there is nothing on the server yet, so
the short unprotected window is harmless). The deployed `example.htaccess`
is just a template and is not active on its own.

## 1 · Run the one-time bootstrap

`first_setup.php` is **POST-only**. You do **not** need a Bearer token (it
is generated by the script) and you do **not** need pre-existing Basic
credentials (POST is exempt from Basic Auth by design). You **do** supply the
viewer username/password that the script turns into the `.htpasswd`.

```bash
curl -X POST https://your-domain.com/dashboard/first_setup.php \
  -H "Content-Type: application/json" \
  -d '{"user":"alice","pass":"SuperSecret123"}'
```

Optional: provide your own Bearer token instead of letting it generate one
(64 hex chars, e.g. `openssl rand -hex 32`):

```bash
curl -X POST https://your-domain.com/dashboard/first_setup.php \
  -H "Content-Type: application/json" \
  -d '{"user":"alice","pass":"SuperSecret123","token":"<your-64-hex-token>"}'
```

**What it does, in order:**

1. validates the input (user non-empty, password ≥ 8 chars),
2. writes `.htpasswd` (bcrypt hash of `user:pass`) **next to the `.htaccess`**
   (app root),
3. copies `example.htaccess` → `.htaccess`, replacing the `__AUTH_USER_FILE__`
   placeholder with the **absolute path of that same-folder `.htpasswd`**,
4. seeds `data/kpi.sqlite` from `data/seed.sqlite` — **only if the live DB
   is missing or empty** (existing data is never touched),
5. writes `data/config.php` **last**, with the real `API_TOKEN`.

**Expected response** (save the token — shown only once):

```text
Setup complete.
API_TOKEN (Bearer) : 9f8c2a1d4e6b7c8d9e0f1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d
Dashboard user     : alice
Live database      : seeded from data/seed.sqlite
IMPORTANT          : save the API_TOKEN now - it is shown only once.
```

The seeded database already contains a **title, subtitle, 5 test metrics
and 7 days of history**, so the dashboard is immediately populated.

## 2 · Safety: it is self-sealing

- **GET** on `first_setup.php` only shows a status (no changes).
- A second **POST** returns `HTTP 409 already initialized` and changes
  nothing — the token, `.htpasswd`, `.htaccess` and live DB are preserved.
- Later deploys can never override these files (they aren't uploaded and
  never enter the FTPS action's sync-state, so they are never touched); they
  only refresh the `example.htaccess` template, so the setup is stable for
  the life of the server.
- **The auth files cannot be downloaded.** The generated `.htaccess` refuses
  to serve itself, `.htpasswd` and `example.htaccess` over HTTP (a
  `<FilesMatch>` deny **plus** a `mod_rewrite` `403`), so the viewer
  credentials are never exposed even though `.htpasswd` sits in the same
  web-accessible folder.

To check status:

```bash
# BEFORE first_setup has run: no root .htaccess exists yet, so GET is open
curl https://your-domain.com/dashboard/first_setup.php        # → Initialized: no

# AFTER first_setup has run: the generated .htaccess protects GETs with
# Basic Auth, so include the viewer credentials
curl -u alice:'SuperSecret123' https://your-domain.com/dashboard/first_setup.php   # → Initialized: yes
```

## 3 · Verify the install

```bash
# as a viewer (Basic Auth is now active):
curl -u alice:'SuperSecret123' https://your-domain.com/dashboard/api/config

# as the feeder (Bearer token — reads and writes):
curl -H "Authorization: Bearer YOUR_SAVED_TOKEN" https://your-domain.com/dashboard/api/config
```

Expected: the seeded title/subtitle (`Operations Dashboard` / `updated daily
at 20:00`) and the **5 seeded metrics**
(`orders`, `emails`, `tickets`, `errors`, `queued`).

## 4 · Adjust the dashboard to your real metrics (optional)

The seed is **test data** so you can see the dashboard working. To make it
yours, update through the API — the changes go into the **live** DB and
persist across deploys:

### 4a. Title / subtitle

```bash
curl -X POST "$BASE/api/config" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"title": "Operations Dashboard", "subtitle": "updated daily at 20:00"}'
```

### 4b. Replace a metric (upsert by key)

```bash
curl -X POST "$BASE/api/config/metrics" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"key":"orders","name":"Orders awaiting fulfilment","why":"fast fulfilment keeps trust","G":0,"Y":2,"O":5,"weight":0.6}'
```

Remove the test metrics you don't want:

```bash
curl -X DELETE "$BASE/api/config/metrics/queued" \
  -H "Authorization: Bearer $TOKEN"
```

### 4c. Wipe the seeded demo history (optional, recommended)

The seed ships **7 days of demo history**. Once you have removed the sample
metrics (or replaced them with your own), clear that demo history so the
dashboard starts empty and only shows the data *you* publish:

```bash
# Deletes ALL stored data points + daily snapshots.
# Keeps the title/subtitle and your metric definitions.
curl -X DELETE "$BASE/api/metrics" \
  -H "Authorization: Bearer $TOKEN"
# -> {"ok":true,"deleted":{"data_points":35,"snapshots":7}}
```

After this, `GET /api/metrics/latest` returns `null` and `GET /api/metrics`
returns `[]` until the first real snapshot is posted.

## 5 · Publish & verify data (the feeder)

The feeder uses **only the Bearer token** (for reads and writes).

```bash
BASE=https://your-domain.com/dashboard
TOKEN='YOUR_SAVED_TOKEN'

# 1) discover the active keys (optional but recommended)
curl -H "Authorization: Bearer $TOKEN" "$BASE/api/config"

# 2) publish a daily snapshot (all active keys required; index is ignored)
curl -X POST "$BASE/api/metrics" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"date":"2026-09-05","metrics":{"orders":2,"emails":5,"tickets":2,"errors":0,"queued":0}}'
#    → {"ok":true,"date":"2026-09-05","index":…,"zone":"…"}

# 3) verify it was stored
curl -H "Authorization: Bearer $TOKEN" "$BASE/api/metrics/latest"
curl -H "Authorization: Bearer $TOKEN" "$BASE/api/metrics"
```

Re-`POST` the **same date** to correct a day (it replaces that snapshot).
Basic Auth also works on the GETs for humans/browsers.

---

## 6 · Open the dashboard

Browse to `$BASE`, log in with the `.htpasswd` credentials you created in
step 1 (`alice` / your password), and you should see the gauges + history.

## 7 · What to hand to the feeder operator

| Item | Value |
|---|---|
| Write + read endpoint | `POST/GET $BASE/api/metrics` · `GET $BASE/api/config` |
| Auth | `Authorization: Bearer <API_TOKEN>` (from step 1) |
| Snapshot payload | `{"date":"YYYY-MM-DD","metrics":{"<key>":<rawValue>, …}}` |
| Correction | re-`POST` the same `date` (replaces) |
| Wipe all history (admin) | `DELETE $BASE/api/metrics` (Bearer; keeps config) |
| Full docs | `$BASE/api/HELP.html` |
